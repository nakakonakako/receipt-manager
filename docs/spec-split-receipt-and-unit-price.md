# 仕様変更: レシート管理と厳密単価比較の分離

最終更新: 2026-08-25

## 1. 一文まとめ

レシート管理アプリ（A）は「どこで何をいくら使ったか」の汎用的な記録・検索・管理に特化する。  
厳密な単価比較（B）は別機能として独立し、手動フォルダで比較対象を管理し、必要時のみ A のレシート DB を一方向参照する。

## 2. 背景と決定理由

### 2.1 問題

| 論点 | 内容 |
|------|------|
| 情報の非対称性 | レシートだけでは g / 個数が取れない。生鮮は事後補正がほぼ不可能 |
| 目的の混同 | 「いくら使ったか」と「100g単価でどこが安いか」は必要な粒度が違う |
| 両立コスト | ラベル写真・紐付け・選択 UI を記録フローに足すと本旨から離れる |
| 中途半端な比較 | メモの総額比較は「動いている感覚」があり、厳密比較の価値を曖昧にする |
| 仮定値 | デフォルト重量などは比較として信用できないため採用しない |

### 2.2 方針決定

- 厳密さを優先する。ざっくり比較を A に残さない。
- A と B を共存させすぎると UI・データモデルが破綻するため、関心を分離する。
- インストアコード / JAN による生鮮重量の汎用自動取得は当てにしない（フォーマット非公開・レシートにコードが載らない）。

## 3. 責務分離

### 3.1 機能 A: レシート管理（本アプリの主目的）

**目的**: 汎用的な支出・購入履歴の記録、検索、管理。

**扱うデータ**

- 日付、店舗、商品名（OCR）、購入金額
- AI / 学習による `main_category` / `sub_category`（既存の自動設定を継続）
- `search_tags` 等、検索・名寄せ補助用の既存フィールド

**やるべきこと**

- レシート撮影・CSV 等による登録
- 履歴の閲覧・編集・ダッシュボード
- **カテゴリ / サブカテゴリを含む汎用検索**（「どこで何を使ったか」を辿れること）

**やらないこと**

- 重量・個数・100g単価の入力・保持を本流にする
- 厳密比較対象の取捨選択 UI
- 値段推移グラフ / 店舗間の厳密比較
- 店頭照会（値札 OCR → 過去単価比較）

### 3.2 機能 B: 厳密定義・単価比較（独立機能）

**目的**: ユーザーが意図した商品だけを、g / 個数 / 全体重量などで厳密に記録・比較する。

**やるべきこと**

- 手動フォルダ（カテゴリ）による比較対象の整理
- 実物確認タイミングでの厳密記録（重量・個数・ラベル写真など）
- 値段推移・店舗比較
- 店頭照会（値札 OCR → B 内データおよび必要なら A 参照）
- 必要時に A のレシート明細を検索して紐付け

**やらないこと**

- レシート抽出側と同系統の **AI 自動カテゴリ生成・付与**
- 仮定パック重量などによる単価表示
- A の登録フローへの埋め込み（A の UI を汚さない）

## 4. カテゴリ設計（今回の追加決定）

### 4.1 A（レシート側）: AI / 学習カテゴリを維持・活用

- 抽出時の `main_category` / `sub_category` 自動設定は **A に残す**（既存実装を活かす）。
- A の主価値は汎用検索なので、**サブカテゴリでの絞り込み・検索**を強化する方向が望ましい。
- ここでのカテゴリは「支出の分類・検索」用であり、厳密比較の対象集合を意味しない。

### 4.2 B（厳密側）: 手動フォルダのみ

- AI が付けた自動カテゴリは **持ち込まない**。
- ユーザーがフォルダ（例: 「鶏むね」「牛乳 1L」「比較したい卵」）をマニュアルで作り、その中に商品（厳密レコード）を入れる。
- 理由: 自動カテゴリが混ざると、比較したくない対象まで検索に引っかかる。
- B のカテゴリは「比較したい集合の意図的な棚」であり、A の会計カテゴリとは別物。

```
A: レシート明細 ──(AI)──▶ main/sub_category  ──▶ 汎用検索・家計分類
B: 厳密レコード ──(手動)──▶ Folder            ──▶ 比較対象の明示的な集合
```

## 5. 連携モデル（一方向）

```
[B 厳密定義・比較]  ──参照・検索──▶  [A レシート DB]
        │
        └── 保持するのは B 側の「紐付け先レシート明細 ID」など
```

- A は B を知らない（A のモデルに厳密フィールドを増やさない）。
- B が日付・店舗・商品名・カテゴリなどで A の明細を検索し、ユーザーが選んで紐付ける。
- 「レシート後から厳密化」も A 画面ではなく **B 側の検索 UI** で完結させる。
- 物理記録が先・レシートが後、どちらが先でも B 側で非同期紐付けできる形を想定する。

## 6. 現行機能の扱い

| 現状 | 変更方針 |
|------|----------|
| メモタブ（値段推移・価格比較グラフ） | **A から完全削除**。同等機能は B に実装・移行 |
| `is_comparable` / メモ用検索 API 等 | A から段階的に削除、または B 移行後に撤去 |
| 店頭照会 | **B に実装**（A のタブとしては増やさない） |
| レシート登録・履歴・ダッシュボード・検索 | A の本流として継続・強化 |
| AI カテゴリ自動設定 | A のみ継続。B には作らない |

## 7. B のデータ方針（確定データのみ）

- 未確定の重量・個数は厳密単価比較の対象外。仮定値は入れない。
- 規格が明確な商品でも、B では「フォルダに入れたもの」だけが比較対象。
- 生鮮はラベル写真 OCR 等で実測情報を入れる想定。取れなければ比較対象にしない。

## 8. 実装フェーズ（目安）

優先度は変更しうる。作業順序の目安。

1. **ドキュメント・方針の固定**（本ファイル）
2. **A: メモタブ削除**（UI・API・関連テーブルの整理）
3. **A: サブカテゴリ等の汎用検索強化**
4. **B: 手動フォルダ + 厳密レコード + 値段推移の新設**
5. **B: A レシート明細の参照・紐付け**
6. **B: 店頭照会**

## 9. 非目標（明示的にやらないこと）

1. レシート登録時の「比較対象にするか」選択
2. A の記録フローへの重量・個数入力の常設
3. 仮定パック重量による単価表示
4. インストアコード / JAN だけで生鮮重量を汎用自動取得することへの依存
5. 単一 UI 内でのざっくり比較と厳密比較の同居
6. B への AI 自動カテゴリの持ち込み

## 10. 用語

| 用語 | 意味 |
|------|------|
| A | レシート管理（本リポジトリの主アプリ） |
| B | 厳密定義・単価比較（独立機能 / 別アプリ相当） |
| フォルダ | B における手動カテゴリ。比較したい商品集合の棚 |
| 紐付け | B の厳密レコードと A のレシート明細を対応付けること |
| 厳密単価 | g / 個 / ml など単位あたりの価格。確定データのみ |
